# Bounded host metadata and small backup V1

Purpose: qualify a portable host publication interface on the actual Windows host. This changes host metadata and exact small backup publication; it does not start Pi research compute, a source, models, capture, a Controller or GUI. Existing source/release/admission files stay immutable. New host metadata lives in mapped metadata/failure/closure groups. No existing successful transport, timer, source, controller or writer protocol is repeated.

Inputs: fresh CPU14 WINDOW_V5 census and independent native closure under fifteen minutes, unchanged policy/checkpoint, original baseline identities and free leases, exact new code/README and retained job-interface hashes. Two retained V81 control receipts are small backup inputs. No release/catalogue/runtime/asset copies. The launcher verifies pins before resuming its single new worker; the worker uses CPU14 before reading.

HostStore reserves 4MiB: metadata2MiB (1MiB/file,24files), failure1MiB (256KiB/file,8files), closure512KiB (128KiB/file,8files), directory/lock allowance512KiB. Its exact four-directory layout and one lock byte are checked on publication. Every name is explicitly mapped. Initial batch byte/JSON/group checks happen before mkdir. Immutable whole-file writes check bytes/count/free floors before creating a .pending file, fsync, rename and verify exact bytes. Failed partials stay unchanged and block ordinary writes in that group; separate diagnostics and closure remain available when their own bounds permit. Failed diagnostic retention is explicit with original byte count/SHA and no retry. No byte truncation is claimed as complete retention.

Windows uses a nonblocking one-byte msvcrt lock; the alternate POSIX fcntl branch is prepared, not qualified by this Windows run. Reparse points, symlinks, nonregular files and multiple links reject when observed. This is a cooperating-writer guard, not a filesystem hard quota or protection against a noncooperating rename race. Directory count/reservation is explicit; it does not measure all NTFS inode/journal metadata. No power-loss/disk-exhaustion/durability guarantee is made.

The exact-backup API preflights all in-memory file bytes, canonical portable paths, case aliases, device names, file/directory collisions, counts and a finite manifest before destination creation. Its scope is at most1MiB/64files/8directories, not the proposed72MiB capture backup. It reserves manifest capacity and holds the same store lock through payload and manifest publication. Partials remain on any failure. It does not accept streamed tar input or start a capture. Each backup file is read back before the final verified manifest. The independent review additionally copies every non-lock fixture file into a flat, uniquely mapped private backup, including renamed partial evidence. Original partial bytes stay in place.

Nineteen changed cases cover exact Unicode/escaping, immutable repeat, unmapped/nonfinite initial batches, first-write and count rejection, injected three-byte partial write, preserved pending rejection, exact reserved diagnostics/closure, diagnostic quota with explicit missing raw, actual two-descriptor lock contention, unexpected-directory preservation, traversal/case/device/file-directory backup rejects, manifest quota before payload, retained-receipt exact backup and repeat rejection. The raw over-limit diagnostic input is the deterministic literal in the pinned fixture source. No unchanged healthy job is rerun. Lock contention is not a multi-process stress claim. Reparse/hardlink guards and portable POSIX branch are source-reviewed, not exercised here.

Execution: retained PrivateApplicationProcess creates one suspended worker on its private invisible desktop, then applies and reads back512MiB job commit, process count1, kill-on-close and CPU4/14 job affinity. Worker narrows toCPU14; coordinator isCPU14. One thread/GPUoff. Wall120s, admission300s,8MiB combined new output; host free floors C50GiB/G75GiB and8GiB available RAM. Existing HOST_EXPORT lease is reused. Actual job cleanup and exact PID/create-time death are independently reviewed. The retained lifetime interface's CANCEL/LIFETIME and fixture harness directories remain admission-scoped, not newly mapped HostStore writers. Source module imports occur before job admission only to prepare the coordinator; no fixture runs before admission. The coordinator itself is not inside the child's job; responsiveness remains a limitation.

Outputs: private field-host-budget-v1-evidence under the campaign pi-native directory: host/{metadata,failure,closure}, fixtures/, lifetime/, verified-fixture-backup/. Real CENSUS/ADMISSION/PREFLIGHT/REGISTERED_OWNER/JOB_ENVELOPE/LAUNCH/RESULT/REVIEW/BACKUP publications use HostStore. The initial external census and native collector receipts still use their retained writers, so this does not qualify every census producer or whole-run host directory limit. Capture allocationV3 remains unapplied/unadmitted; no policy revision/reset/delete. Per-producer whole-run reservations and installed LIVE binding are still required.
