# Journal-derivative application source context and prestart checks

The component banks remain bound to the immutable catalog source. Actual N4
application evidence needs the separately qualified complete-event-journal
derivative. `application_source_context.py` makes that distinction explicit and
reconstructs the source/gallery lineage instead of silently replacing paths in
an old plan. It does not admit inference or accept a shortlisted configuration.

Inputs are NATIVE_JOURNAL_RETENTION_CHECK_V1.json, the original application
prestart qualification, their exact private receipts, parent/derivative source
inventories, catalog bytes, research-gallery preparation and runtime metadata.
It verifies all source files and the two allowed edits plus two additions,
unchanged common frontend and prediction files, the fixed 256-MiB event policy,
and exited qualification helpers. It creates a copy of gallery preparation whose
only changed value is the location of the byte-identical catalog. Original E
vectors, names, missing-roster counts, calibration policy and all gallery payload
bindings are unchanged; no enrollment, threshold tuning or vector extraction runs.

`prepare(fresh_directory)` outputs GALLERIES_PREPARED.json and CONTEXT.json.
`review(context_binding)` independently reconstructs them from the qualified
parents. The context retains both `component_*` parent bindings and new
application bindings, with status PREPARED_APPLICATION_SOURCE_CONTEXT_ONLY.
The immutable context makes no claim that application tests ran; a separate
qualification receipt records those results.

`probe_journal_application_prestart.py run` performs four lineage corruption
checks, then nine checks on an invisible private Windows test desktop using the
qualified V3 suspended-process/job launcher. The actual common Tk/Controller is
prepared and closed for all 16 implemented backend rows, and the seven existing
viewport-hook regressions are reused. One additional check imports all three
engine families and checks their actual shared journal factory with synthetic
text. No engine instance or source is started. Resident/ONNX model acquisition,
file-source construction and Controller file/live start calls are forbidden
during real application preparation. Existing research gallery data is read only.

The probe pins helper and test child to CPU14, disables GPU visibility and uses
one math thread. D1 retains CPU4. It checks active exact D1 ownership and protected
source bindings before and after, the helper lock, a 720-second outer limit,
240-second child limit, 8-MiB output bound, C:50/G:75 GiB free-space floors and
the shared 50-GiB payload allowance with its conservative 6-GiB reserve. It never
switches the input desktop, injects input, enumerates microphones or connects to
the Pi. Only its exact newly created private job may be cleaned up on failure.
This is an independent model-free check, not a controlled resource measurement;
the production exclusive admission gate remains unchanged.

Outputs are private ADMISSION.json, source snapshots, application context,
lineage/gui test logs, per-backend preparation/closure and observer files,
synthetic factory files, child registration, exact private-process lifetime and
RESULT.json or preserved FAILED.json. Normal success requires the exact child
and every observed job member to have exited, an empty job without forced
termination, unchanged input-desktop observations, and all 16 Controllers closed.
