# Realtek playback scheduling review — 2026-09-05

The original blocking Realtek playback path cannot use an empty `underflows` list as evidence of uninterrupted acoustic playback. Both reviewed takes requested `latency='high'` but reported only 0.022 s of actual stream latency. Writing chunks of 4096 frames (85.33 ms at 48 kHz) does not establish that much hardware buffering.

The installed sounddevice 0.4.6 reports PortAudio `V19.7.0-devel, revision 147dd722548358763a8b649b3e4b41dfffbcfbb6`. In that exact revision's WASAPI `WriteStream`, the ordinary final return distinguishes host error from success; this implementation contains no `paOutputUnderflowed` return. Consequently the Python `write()` boolean cannot detect every underrun. The callback processing loop also initializes its callback flags to zero, so callback flags alone are not a complete acoustic continuity test. Callback mode creates a native worker which attempts MMCSS priority boosting and primes its output buffer. [Exact installed-revision PortAudio WASAPI source: WriteStream; WaspiHostProcessingLoop; StartStream; ProcThreadEvent](https://raw.githubusercontent.com/PortAudio/portaudio/147dd722548358763a8b649b3e4b41dfffbcfbb6/src/hostapi/wasapi/pa_win_wasapi.c)

The queued USB telemetry worker performs its roughly 3300 read attempts per second in a separate C# process. Its retry JSON is written there, while Python receives only successful telemetry samples. It therefore does not directly hold the audio process's Python GIL. It can still compete for CPU, disk and driver scheduling. Native CFFI calls release the GIL, so the old blocking PortAudio write's internal refill loop should not be described as holding the GIL throughout; Python gaps between writes and Python callbacks still require it. [CFFI reference: GIL behavior](https://cffi.readthedocs.io/en/stable/ref.html)

`measurement_app/playback.py` now provides the same `separate_playback(device, wave, gain_db, channel, stop, receipt)` interface. It prebuilds a float32 channel array, requests 0.15 s latency, lets PortAudio select callback buffer sizes, and preallocates numerical receipt storage. It records every callback's source offset/count, status flags, host arrival time and PortAudio DAC/current timestamps. JSON conversion occurs after stream closure. The 0.15 s request is a scheduling margin, not an exact promised latency; the actual value is retained. The source-frame trace proves what was submitted, not what the loudspeaker physically emitted.

The callback fills the entire output buffer, pads the final partial buffer with zeros, and requests `CallbackStop`. Completion requires the finished callback, which sounddevice documents as following buffer draining. Cancellation follows the same draining path with a 1.5 s abort fallback; a normal completion wait is bounded by signal duration plus 5 s. Native driver calls themselves remain subject to the driver's behavior. Callback errors and cleanup errors remain in the receipt. [sounddevice 0.4.6 callback, latency and finished-callback contracts](https://python-sounddevice.readthedocs.io/en/0.4.6/api/streams.html)

Eight offline unit tests passed on 2026-09-05 without opening audio devices: variable buffer source continuity and zero padding; cancellation; callback failure; receipt-capacity failure; completion/drain receipt; start plus cleanup error preservation; invalid audio rejection; cancellation before device access. Run with `python -X utf8 -m unittest discover -s tests -p test_playback.py -v` using the bundled Python runtime.

Hardware acceptance remains independent: repeat the exact acoustic markers while capturing raw microphones and the digital continuity sequence, compare marker intervals and sweep alignment, and retain any discrepancy. This scheduling change does not establish that the previously observed marker anomaly was an underrun, remove speaker processing, synchronize Realtek and XVF clocks, or calibrate acoustic latency.

## Callback startup failure and thread-local COM correction

The first callback hardware take, `TAKE_20260905T225235_502465Z_95a5bd`, opened its Realtek stream with 0.16 s actual latency but failed at start before producing any callbacks. The reported PortAudio error was -9999 with an unrelated WDM host-error string. This take remains failed.

In the installed PortAudio revision, nonblocking WASAPI `StartStream` calls `MarshalStreamComPointers` on the calling thread before creating its callback worker. That operation calls `CoMarshalInterThreadInterfaceInStream`. Its failure branch returns the generic host error without updating the global host-error record; a prior WDM error can therefore remain attached. Blocking startup skips marshaling. This is a source-supported explanation consistent with the failure, rather than a recovered native HRESULT from that failed take. [Installed WASAPI StartStream and COM marshaling](https://raw.githubusercontent.com/PortAudio/portaudio/147dd722548358763a8b649b3e4b41dfffbcfbb6/src/hostapi/wasapi/pa_win_wasapi.c)

COM initialization belongs to each calling thread. PortAudio's initialization helper initializes its own calling thread with STA semantics and balances cleanup on that same thread. Initializing sounddevice on the app's main thread does not initialize a subsequently created playback thread. [PortAudio COM helper](https://raw.githubusercontent.com/PortAudio/portaudio/147dd722548358763a8b649b3e4b41dfffbcfbb6/src/os/win/pa_win_coinitialize.c)

The replacement now calls `CoInitializeEx(NULL, COINIT_APARTMENTTHREADED)` on the playback thread before format checking, opening or starting the stream, matching PortAudio's helper. Both S_OK and S_FALSE acquire a reference and are balanced after stream close. RPC_E_CHANGED_MODE uses the already existing apartment without acquiring or releasing a reference. Other HRESULTs fail explicitly. The receipt retains the HRESULT, thread identity and reference-release result. [Microsoft CoInitializeEx contract](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-coinitializeex), [CoUninitialize contract](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-couninitialize)

Twelve offline tests now pass, including COM reference balancing, preserving another apartment owner, preventing audio access on COM initialization failure, and closing the stream before COM cleanup after a start failure. A separate local COM-only probe on a fresh Python thread is retained in `tmp/playback_com_thread_probe.json`; it opens no audio stream and performs no XVF control calls. Priming, callback buffering and the absence of a silent blocking fallback remain unchanged. Successful acoustic hardware playback still requires a new take.
