# H2 Windows atomic-publication retry

## Purpose

`h2_windows_atomic_retry_bootstrap.py` protects the unattended H2 campaign from
short Windows sharing violations while an existing JSON status or validation
file is atomically replaced. It changes no model, input, threshold, metric, or
scientific output. It retries only Windows errors 5, 32, and 33 for a bounded
7.15 seconds and then preserves the original failure.

The bootstrap also prepends the dedicated
`scripts/h2_atomic_retry_child` directory to `PYTHONPATH`. Python therefore
loads its `sitecustomize.py` in isolated enrollment and model-worker
interpreters, propagating the identical bounded retry to child processes. This
is necessary because an in-process `os.replace` policy is not inherited across
`subprocess` boundaries. The child policy still retries only the atomic rename;
it does not change generated bytes or scientific computation.

The normal PowerShell launcher uses this bootstrap automatically. Linux and
other platforms keep the standard `os.replace` behavior.

## Inputs and outputs

Inputs are the same H2 controller action and arguments documented in
`app/h2_product_program/README.md`.

Operational outputs are kept on C: below the selected campaign workspace:

- `storage_maintenance/windows_atomic_publication_policy.json`: checksum-bound
  retry policy, launcher identity, child-policy identity, and propagation mode;
- `storage_maintenance/superseded_atomic_publication_policies/`: immutable
  predecessor receipts retained when the operational policy is upgraded;
- `logs/windows_atomic_publication_events.jsonl`: append-only retry, recovery,
  or exhaustion events. No event is written when publication succeeds on the
  first attempt.

These compact files map the operational recovery for reproducibility. They do
not duplicate audio, models, embeddings, or result payloads.

The augmented final package retains both executable sources as
`reproducibility/storage/code/h2_windows_atomic_retry_bootstrap.py` and
`reproducibility/storage/code/h2_atomic_retry_child_sitecustomize.py`. Its
validator checks both hashes against the signed policy receipt and fails closed
if either source is missing or differs.

Read-only actions (`Audit`, `Validate`, `Plan`, and `Status`) and the supported
`LaunchDemo -DryRun` invocation do not create the policy receipt, event log,
workspace, or result directories. The launcher removes inherited receipt-path
environment variables before those actions, so a shell reused after a
scientific run stays read-only. Mutating actions install or verify the durable
policy receipt before they publish campaign state. The wrapper rejects
`-DryRun` on other actions instead of silently running a mutating action.

## Run from PowerShell or Anaconda Prompt

Use the normal launcher so workspace/result paths and logs are configured:

```powershell
Set-Location 'C:\Users\amiri\Documents\GitHub\just-peachy\Software Validation from Datasets\Evaluation Tool'
./scripts/run_h2_product_program.ps1 -Action Resume -RetryFailed -Background
```

For a direct foreground status check through the same bootstrap:

```powershell
Set-Location 'C:\Users\amiri\Documents\GitHub\just-peachy\Software Validation from Datasets\Evaluation Tool'
C:\Users\amiri\anaconda3\python.exe ./scripts/h2_windows_atomic_retry_bootstrap.py Status
```

The controller inputs, scientific result directories, summaries, and final ZIP
remain unchanged. Do not run two controllers against the same workspace; the
campaign lease still enforces single ownership.
