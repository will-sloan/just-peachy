Goal:
Build the enrollment data structure and CLI/workflow for associating one or more speaker embeddings with a speaker name.

Required schema:
Define an enrollment database schema that records, at minimum:
- `speaker_id`
- `display_name`
- `prompt_id`
- `audio_path`
- `embedding`
- `model_id`
- `created_at`
- `notes`

Functional requirements:
- Support multiple exemplars per speaker.
- Support future use of both averaged centroid embeddings and exemplar-by-exemplar matching.
- Create a CLI that enrolls speakers from existing WAV files first.
- Do not implement live microphone enrollment.
- The enrollment DB must record model/version metadata, not just vectors.
- Enrollment DB must be versioned/reproducible and independent of any UI.
- Enrollment DB should be loadable in a separate process.
- If an existing matcher test or matcher module exists, integrate the enrollment DB narrowly enough that matcher tests can load/use it. If no matcher exists yet, do not invent a broad matcher architecture; add only store-level validation needed by this milestone.

Validation and checks to implement:

- Embedding duration coverage per enrolled speaker.
- Model-version consistency: stored embedding model matches runtime matcher model.
- Warnings for model-version mismatch.
